# Test-only MongoDB group transaction tracer

Run `npx jest --config test/jest-e2e.json --runInBand mongodb-group-transaction.e2e-spec.ts` with Docker available. Testcontainers starts and removes a disposable single-member `mongo:7` replica set; no external MongoDB URI is used. The fixture requires the image to be available locally or pullable.

The original fixed two-stream fixture reserves increasing positions in one transaction. Command monitoring checks the shared session/transaction and majority+journal commit. A duplicate-key error verifies whole-transaction rollback. A separate simplified tracer evaluates ANY, NO_STREAM, EXISTS and numeric revisions serially, including repeated streams; failed validation does not stage an event or consume a position. A two-client concurrent race checks one NO_STREAM winner, independent peer successes, unique ordered positions and contiguous positions within the winning group. The counter is touched transactionally before reading stream state; results are rebuilt inside the driver transaction callback and returned after commit. One run of this race does not prove every interleaving or general zero-increment locking semantics. The direct-driver fixtures are not the adapter protocol or production data model: in particular, unlike the production path they do not consume positions for rejected requests, support only one event per request, and intentionally test same-stream grouping although the design proposes excluding it. They do not test official-client behavior, multiple adapter instances, visibility during commit, retries under injected failures, unknown outcomes, cancellation, tombstones, overflow or failover. Validation failure isolation is not write-error isolation: a command error aborts the group. A single-member majority is not replication redundancy. This is not a benchmark or evidence of production parity or the throughput target.

TDD record: the stale-revision isolation slice failed against an explicit not-implemented tracer and then passed against real MongoDB. The same-stream and two-client assertions were added after that implementation and were not observed failing for missing behavior, so strict red-green was not achieved for those slices. The original rollback test likewise had no separate red phase. Full e2e and multi-node failover suites are not established by these targeted tests.

The isolated group runner's cleanup-failure and invalid-limit regressions were observed failing before their fixes. Additional injected work/commit failure, retry, and real Mongo cleanup tests were added after the fix as coverage, not separate red-green cycles. Session cleanup is attempted once; errors are suppressed to preserve the primary outcome, so a cleanup failure is currently unobservable and may leave driver resources until later reclamation. Production integration needs a non-throwing cleanup-error reporting channel and bounded cleanup, plus reconciliation for uncertain commits; never infer committed from cleanup. A hanging `endSession` can delay publication even after commit, and shutdown may settle the batch unknown first. These are isolated prototype tests, not performance or production-wiring evidence.

## Test-only official-client RPC bridge

Run `npx jest --config test/jest-e2e.json --runInBand test/mongodb-group-rpc.e2e-spec.ts`. This fixture intercepts eligible single-event ANY appends only; it is not production wiring. Two official-client appends can share one majority+journal transaction, and a tombstoned member is rejected independently of a healthy member.

The lost-ack injection commits successfully and then throws. Both dispatcher outcomes are `unknown`, the official-client requests reject with `UnknownError`, and both events are readable; the test verifies no retry of the uncertain writes. This is a bounded injected acknowledgement loss, not proof for every transport failure.

Two additional official-client races use two independently constructed adapter instances and a disposable single-member replica set. One pauses a tombstone before commit while a grouped append competes; the other confirms the first member's counter reversal was acknowledged, holds its group before commit, and races a second-adapter tombstone. A gate requires a correlated server reply (successful or a Mongo server error), or a `$currentOp` match by session and transaction, before releasing the owner. A driver command-start event alone is not treated as server arrival. Successful positions, surviving `$all` events, rejected tombstoned writes, and majority+journal commit commands are checked. The first race exposed aborted group requests hanging in the client's BatchAppend stream; before the controller fix the bounded settlement assertion failed, and after mapping aborted outcomes to correlated unknown errors it passed. Unknown is conservative and does not promise the caller a definitive abort.

These tests exercise only specific interleavings, a single-node majority, and a test-only bridge using single-event ANY appends. They do not establish failover, multi-node durability, arbitrary workloads, production group integration, or throughput. The competing work may abort rather than retry, and its caller must reconcile uncertain outcomes. The tests do not prove that command monitoring events are authoritative for production replay decisions.
