# Test-only MongoDB fence experiment

Run `npx jest --config test/jest-e2e.json --runInBand test/mongodb-fenced-tracer.e2e-spec.ts` with Docker. Two independent clients use a disposable single-node MongoDB 7 replica set. The initial fence is created by the fixture; acquisition is an explicit compare-and-swap on owner and epoch with majority+journal, and every protected transaction increments that same fence document before inserting an event, with majority+journal commit. An epoch is never intentionally reused in the experiment. A stale transaction with an existing server snapshot is rejected on its fence write, and its commit is rejected; a separate test pauses before the first transaction operation and takes over. Concurrent acquisition and transaction conflicts, unique positions, and client/container cleanup are exercised.

The combined admission experiment uses two independent clients and separate bounded process-local queues. A running and a queued old-owner write are rejected after manual takeover; a queued cancellation is skipped and overflow is rejected, while two new-owner writes are serialized and read back in unique order. Cancellation is checked only when the queued operation reaches the head: it does not settle promptly or free capacity while blocked and does not cancel a running operation. All modeled event mutations use the fence; fixture initialization/reset and index creation are not modeled mutations. There is no automatic application retry or lease expiry.

A deliberately adversarial shared-token experiment starts two independent serial queues of 20 writes each. One local run observed 26 acknowledged, 14 rejected in 109 ms, with 26 distinct consecutively positioned events on majority readback. Separate queues do **not** serialize each other; the fence can produce conflicts, and sharing a token across owners is not a safe ownership protocol. This small single-node result is scheduling-dependent, not a benchmark or evidence for the >=80% production target. The driver may retry at wire level. No inference about uncertain errors is authorized by this conflict-free readback.

TDD scope: the queued-cancellation behavior was observed failing before its test-only implementation and then passing. The combined integration and contention tests characterize existing fence/admission composition and were not observed failing first; full strict TDD was not achieved.

The separate `npx jest --config test/jest-e2e.json --runInBand test/mongodb-fenced-election.e2e-spec.ts` scenario requires local Linux Docker host networking. It creates three disposable MongoDB 7 members, pauses the primary and an old owner's transaction before its first server operation, waits for a different primary, explicitly acquires the next epoch with majority+journal, then commits a new event. Resuming the stale owner must return `fence rejected`, and a majority read verifies the acknowledged events and distinct consecutive positions while the former primary remains paused. The test unpauses it in cleanup. Removing the owner/epoch predicates from the protected write was separately checked to make this scenario fail because the stale write commits. This is characterization of existing test-only code, not a TDD red-green implementation cycle.

**This is not a time-based lease or a production serialization solution.** No expiration, timeout, renewal, wall-clock or automatic takeover is implemented or claimed. Whoever invokes the explicit CAS can revoke a live writer; takeover authority, lease semantics and liveness are unproven and must fail closed. Contention can abort writers rather than queue them; errors are propagated, not automatically replayed. Commit/acquisition errors can be uncertain, and the caller must not infer abort or replay from them. Driver wire-level retries are not controlled. The test reset is fixture-only and would invalidate epoch monotonicity if used outside an isolated database. Integer limits are guarded for expected fixture data, not a validated durable schema. The election scenario does not pause an already-executing server transaction or a separate owner process, nor cover crashes, arbitrary partitions, lost acknowledgements, official-client contract, nonparticipating mutation bypasses, throughput or production integration. Test monitoring does not prove safety against nonparticipating clients or forged evidence. Full strict TDD was not achieved for the original tracer: the initial takeover and pause-hook slices were observed red then green; the snapshot and contention characterization tests were added after implementation, with no behavioral RED. This does not satisfy production readiness or the >=80% throughput goal.
