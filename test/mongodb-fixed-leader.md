# Fixed-leader routing tracer (test only)

Run `npx jest --config test/jest-e2e.json --runInBand test/mongodb-fixed-leader.e2e-spec.ts` with Docker. This is a disposable experiment, not application wiring. Two logical client workloads in the same process use independent loopback TCP connections to one designated listener. Every modeled event write goes through that listener's single bounded `SerialAdmission` and its one MongoDB client, then `protectedWrite` checks and increments the owner/epoch fence in the same majority+journal transaction as the insert. The fixture alone initializes the fence and creates indexes. It is not an official Kurrent client or application-level test.

A local run on a disposable single-node MongoDB 7 replica set attempted 100 concurrent writes (50 per logical client): 100 acknowledged, zero unknown, 460 ms, about 217 writes/second. The writer's instrumented maximum active protected writes was one. Majority readback found 100 distinct names and consecutive unique positions. This is a small, single-run observation, not a benchmark against KurrentDB or evidence for the >=80% target. The listener test also fills capacity while an accepted write is gated, verifies the excess is rejected, and verifies the accepted caller times out unknown even though its write later commits once. After the listener closes, connection refusal is rejected; after a manual fence revocation, the stale writer returns unknown and writes nothing. No application-level retries or replay are performed; the Mongo driver may retry at wire level.

TDD scope: the initial test failed because the routing module was missing, then passed after implementation; the admission/timeout gated test failed because the gate was absent, then passed after the hook was implemented. The final shutdown-drain cleanup was not separately observed failing first.

## Separate-process pre-commit crash

Run `npx jest --config test/jest-e2e.json --runInBand test/mongodb-process-crash.e2e-spec.ts` with Docker. A separate leader OS process stages a fence increment and event insert in a real MongoDB transaction, then signals a gate immediately before calling `commitTransaction`. A separate client process submits over TCP. The test sends SIGKILL to the gated leader, verifies the client receives `unknown`, and starts another OS process to manually acquire the next fence epoch and commit two events. A majority read verifies exactly those two distinct names at positions 1 and 2; the old staged event is absent. Child IPC and termination have timeouts and cleanup kills surviving children. The disposable single-node MongoDB replica set uses a five-second transaction lifetime so the orphaned transaction's lock is eventually released; takeover is not immediate and is bounded by the test timeout.

This covers only a kill **before the commit call is made**, not a kill during commit, after commit, a lost acknowledgement, automatic failover, or production RPC/client behavior. The test-only hook and TCP protocol are not production wiring. The initial test failed because the separate worker did not exist; after implementing it, takeover initially timed out under MongoDB's default transaction lifetime and passed with the disposable fixture's reduced lifetime. It does not establish the >=80% throughput target.

## Separate-process post-commit crash

The same command also runs a distinct post-commit case. The leader gates after `commitTransaction` has returned successfully (majority+journal write concern) and before sending the TCP response. The parent additionally reads the committed event with majority read concern before killing the gated process. The separate client reports `unknown`; a separate process explicitly acquires a higher fence and writes two more events. Majority readback checks the original event appears exactly once and all three positions and names are unique and consecutive, with no application-level replay. The initial test failed because the post-commit worker role was absent; it passed once the test-only gate was added.

This is a process crash after MongoDB acknowledged commit, **not an in-flight network partition**, a crash during commit, or a lost MongoDB commit acknowledgement. It does not test production RPC/client behavior or automatic failover, and does not establish the >=80% throughput target.

**Operational limitations:** This is a fixed single writer and a single point of failure, not HA. There is no leader discovery, automatic failover, lease expiry, replay, reconciliation API, authenticated transport, durable request queue, production request wiring, or protection against writes that bypass this test-only listener/fence. The admission bound counts running and queued operations, not open sockets or bytes, and is not a complete resource bound. A successful TCP connection followed by timeout/disconnect is unknown, never proof of abort; an unknown may commit and must be reconciled before any retry. Explicit capacity rejection and failure to establish a connection are rejected because that invocation has not been submitted to the listener. Revocation is explicit and may evict a live writer; no safe takeover authority is established. Shutdown closes client sockets and waits without a time bound for admitted operations, which can hang. The active counter verifies only this listener's modeled protected-write calls, not absence of nonparticipating MongoDB transactions. No multi-node partition, during-commit crash, real lost-ack network fault, production throughput, or general safety claim follows.
