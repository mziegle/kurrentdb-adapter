# Experimental MongoDB event store

Set `EVENT_STORE_BACKEND=mongodb`, `MONGODB_URI` (default `mongodb://localhost:27017/?replicaSet=rs0`), and optionally `MONGODB_DATABASE` (default `kurrentdb_adapter`). The server must be a replica set or sharded deployment that supports multi-document transactions. PostgreSQL remains the default (`EVENT_STORE_BACKEND=postgres`). Use a dedicated MongoDB database; no migration from PostgreSQL or arbitrary prior MongoDB schemas is provided.

## Stream subscription cursor compatibility

Individual-stream subscriptions treat a numeric `fromRevision` as the last processed revision and resume strictly after it. In contrast, ordinary forward stream reads include the specified revision. `START` includes revision zero; `END` starts after the current end. This corrects earlier MongoDB adapter versions that redelivered the numeric cursor event: consumers relying on that replay should adjust their checkpoints. Official-client differential tests against disposable MongoDB and `docker.kurrent.io/kurrent-latest/kurrentdb:latest` cover revisions 0 and 1, one future revision, START/END, a fresh subscription after restart, and max-count retention. A separate MongoDB test covers numeric resumption and live writes through different adapter instances. These tests do not prove automatic reconnect, concurrent END initialization, all retention policies, failover, or parity across KurrentDB versions. Restart testing creates a new subscription from a saved revision; it does not test in-flight automatic reconnect.

Run the differential suite with `npx jest --config test/jest-e2e.json --runInBand mongodb-subscription-cursor.e2e-spec.ts`; it starts disposable servers and requires Docker. Do not set `KURRENTDB_TEST_CONNECTION_STRING` when a disposable reference server is required.

## $all subscription positions

Official-client differential tests against disposable MongoDB and `docker.kurrent.io/kurrent-latest/kurrentdb:latest` cover a saved exact position, a position within a multi-event append, a far-future position (no delivery within 700 ms after a write), and filtered START/END catch-up followed by ordered live delivery. They observed resumption strictly after the supplied event position. A separate MongoDB test exercises history and ordered live delivery across adapter instances. Run `npx jest --config test/jest-e2e.json --runInBand mongodb-all-cursor.e2e-spec.ts mongodb-streams.e2e-spec.ts`; Docker is required. These cases do not establish parity for arbitrary commit/prepare pairs, cursor crossing of a future position, concurrent END initialization, checkpoints, reconnect, failover, or other KurrentDB versions. The reference image uses a mutable `latest` tag.

## Concurrent END initialization coverage

The MongoDB stream and filtered `$all` tests pause immediately after the initial END cursor query returns, commit a two-event append through a separate adapter instance, then resume the subscriber. Both events are observed once in order, followed by a later sentinel; the event committed before the cursor is excluded. The tests use the official client and a disposable single-member replica set; the pause is instrumentation of the MongoDB driver, not a network or database failure. The same precise internal interleaving cannot be imposed on the KurrentDB reference. Existing differential tests cover the non-concurrent END boundary, not this race. Commits before the cursor query, simultaneous transactions across the read boundary, empty streams/databases, unfiltered `$all`, deletion, scavenge, failover and reconnect during initialization remain unverified by this race test. No production-readiness conclusion follows.

## Retry and duplicate-ID limitations

A repeated single-event `NO_STREAM` append is acknowledged without another event write only when the stream still consists of exactly that one initial event, no soft deletion occurred, and ID, metadata fields, custom metadata and data match. Data and custom metadata are compared byte-for-byte. It returns the stored final revision and position. Matching is deliberately stricter than ID-only matching to avoid acknowledging a request with different content. Retention/scavenging can remove evidence and prevent recognition. Multi-event retries, retries after further events exist or after deletion/recreation, and retries using explicit revisions, `ANY`, or `STREAM_EXISTS` are not recognized; a failed or timed-out request may have committed and must be reconciled before another write. Do not assume an error means no data was written. Exact retry matching is performed inside the same transaction as stream-state checking, but this is not a durable request ledger or a failover test.

An official-client differential test against the container image `docker.kurrent.io/kurrent-latest/kurrentdb:latest` confirms an exact single-event `NO_STREAM` retry succeeds without duplicating the stream event and that both backends accept the same ID on another stream. Other duplicate-ID and retry cases, positions, changed payload behavior, and results across KurrentDB versions remain unverified. A recognized retry still advances the MongoDB global counter, leaving a position gap; it does not write an event.

### Upgrading the legacy event-ID index

Back up the database and stop **all old adapter instances** before upgrading. On startup the new adapter first ensures the stream-revision and position uniqueness indexes, then drops the old adapter-created unique `{eventId: 1}` index named `eventId_1`. No event documents are deleted. Startup fails if required index creation or the drop fails (for example, due to insufficient privileges). Repeated or concurrent upgraded startups tolerate an already-dropped index. Operator-created indexes with other names are not removed and can still reject valid writes; inspect them separately. Do not run old and new binaries together: an old instance may recreate the unique index, or fail to start after duplicate IDs are stored. Downgrade requires resolving duplicate IDs without data loss and is not automatic; restoring a backup may be necessary. This upgrade does not repair previously failed writes.

## Append concurrency

Experimental group commit is disabled by default and requires the explicit
opt-in flag and single-adapter acknowledgement; see [group dispatcher](mongodb-group-dispatcher.md#experimental-application-integration).
The acknowledgement is not enforcement or fencing and does not make this
experimental backend production-ready. Do not use it on shared or production data.

The ordinary append path has no local append admission queue; experimental group commit has its own bounded dispatcher. MongoDB's transactional global counter remains the cross-instance serialization point. Cancellation context is propagated to the backend, but MongoDB appends do not currently use it to cancel transactions; a timeout or cancellation does not prove a transaction was aborted. Reconcile uncertain outcomes before retrying. An earlier experimental local queue was removed after it failed to meet the performance criterion; its exploratory results do not establish group-commit performance.

## Durability and connection settings

The adapter sets client write concern to `{ w: "majority", j: true }`; transactions inherit it, including snapshot transactions and scavenging, unless a transaction explicitly overrides it. Index creation also uses it. This explicitly requests acknowledgement from the calculated voting data-bearing majority after journaling, independent of the server's configured default or `writeConcernMajorityJournalDefault`. The Node driver 6.22.0 otherwise sends an explicit client/URI concern if supplied, or defers to the server default; that default can be `w: 1` in certain arbiter configurations or be administratively changed. See [MongoDB write concern](https://www.mongodb.com/docs/v7.0/reference/write-concern/) and [driver transactions](https://www.mongodb.com/docs/drivers/node/current/crud/transactions/).

URI `w=0`, `w=1`, and `journal=false` do not weaken this policy. Custom numeric `w` values above 1 and tagged policies are rejected at construction rather than silently replaced with a potentially weaker or incomparable majority policy; remove them to use the adapter policy. This may require reconfiguration of existing deployments. TLS, authentication, and certificate validation options are not relaxed or overridden. Journaling must be supported: servers that reject `j: true` fail the write rather than falling back. A single-member replica set has a majority of one and provides no replication redundancy; use appropriately configured, independently durable voting data-bearing members for redundancy. No startup probe can prove future quorum, stable storage, or crash durability. Quorum loss can block writes, and timeouts or lost commit responses may leave outcomes unknown; do not assume a failed request means an aborted transaction. The driver retries certain transient transaction and commit errors, but this is not application-level idempotency. Configure appropriate MongoDB URI timeouts and reconcile uncertain outcomes before retrying. `$all` and subscription reads use the driver's configured/default read concern; they are not guaranteed to hide all data that could roll back during failover.

This is an incomplete backend, not a production-compatible replacement. It supports transactional append and batch append, optimistic expected stream revisions, unfiltered individual-stream reads and subscriptions, plus `$all` reads and subscriptions with optional stream-name or event-type prefix/regex filters. Subscriptions poll MongoDB every 100 ms and read committed stream revisions in order, including writes from other adapter instances. MongoDB serializes append transactions on a single global counter. This limits throughput but ensures assigned positions and stream state commit together. Positions and revisions use JavaScript safe integers, not the full 64-bit KurrentDB range: requests and values encountered beyond ±9,007,199,254,740,991 are rejected, and transactions abort if an allocated counter or revision crosses that limit. Errors may surface as generic RPC failures or retries (especially batch append); clients should configure deadlines. This is not a repair mechanism for data already rounded or corrupted by older versions or external writers, and it does not scan all stored data for unsafe values. Full 64-bit compatibility is not implemented. It creates unique indexes on global position and stream/generation/revision, not event ID. Retry/idempotency semantics are not fully Kurrent-compatible.

Soft delete and tombstone check expected revisions transactionally. A soft-deleted stream can be recreated with `NO_STREAM`; revision numbers continue and older events remain in `$all` but are hidden from stream reads. Tombstones add a `$streamDeleted` event and reject later writes. Concurrent changes to an existing stream conflict on the stream document; append and tombstone also serialize on the global counter. Each individual-stream read and each individual-stream subscription polling batch reads state and events in a MongoDB snapshot transaction. A batch already read may still be delivered after a concurrent deletion; subsequent polls observe the deletion. The end-of-stream subscription starting cursor is established separately, and broader deletion, reconnect and failover semantics remain unverified. Polling now incurs a read transaction every 100 ms per active subscription; scalability has not been measured.

Metadata is stored as ordinary `$$` stream events. `$maxCount`, `$maxAge` (seconds), and `$tb` apply to individual-stream reads and subscription batches; the latest valid `$metadata` JSON event replaces the previous policy. Metadata events and events hidden by retention remain in `$all` until scavenging. Policy updates and metastream appends commit in one transaction; stream reads and subscription batches observe stream state, policy, and events in one snapshot. A batch already read may still be delivered after a policy change. Metastream delete and tombstone operations remain unsupported. Retention interaction with soft deletion, unusual metadata values, subscription reconnect, and failover has not been comprehensively verified.

Scavenging is **disabled by default**: start returns gRPC `UNIMPLEMENTED` and start/stop are omitted from feature advertisement. Setting `MONGODB_UNSAFE_ENABLE_SCAVENGE=true` exactly before starting the adapter enables and advertises experimental scavenging; all instances must be configured deliberately. Never enable it on data you cannot afford to lose. Back up and verify recovery first. It permanently deletes events, may violate KurrentDB compatibility, and is not production-ready. Start returns immediately and stop requests cancellation between streams; it does not roll back completed work or interrupt a transaction. A per-stream transaction locks the global counter shared with writes before reading the current policy and stream state. It removes hidden older events, superseded metadata events, and prior deleted or tombstoned history, while keeping the latest stream event and stream revision. Soft-deleted history remains eligible after recreation. Other instances can start separate scavenges; operations serialize through the counter. Errors are logged but there is no completion/status API, persistent job state, resumability, or cross-instance cancellation. Each stream is deleted in a single unbounded transaction, which can fail for large streams; performance and failover have not been tested. Concurrent creation of streams during a scan may require another scavenge. Only a subset of semantics and concurrency has integration coverage.

Explicitly unsupported: backwards subscriptions, link resolution, individual-stream filters, metastream deletion/tombstoning, and statistics. `$all` filters use MongoDB's regular-expression engine; regex syntax and PostgreSQL LIKE wildcard behavior are not guaranteed identical. Filter checkpoints are not implemented. `$all` polling reads matching committed rows in position order, and does not advance its cursor when no matching rows are found; sparse filters may repeatedly scan old positions. Load benchmarks and comprehensive replica-set failover tests have not been performed, so neither production readiness nor performance parity with KurrentDB is established. The global write counter and per-subscription polling are potential bottlenecks. MongoDB server-features omits monitoring statistics, persistent subscriptions, user management, and no-op administrative operations (merge indexes, restart persistent subscriptions, resign, node priority and shutdown). It retains stream methods, gossip and server-features; experimental start/stop scavenge are advertised only with the unsafe opt-in; `24.0.0` is a compatibility negotiation value, not a claim of KurrentDB parity. The Node client's `$all` persistent-subscription creation checks this advertisement and rejects it as unsupported, but some client methods do not consult capabilities, and the underlying stub RPCs can still return misleading success. Do not use persistent subscriptions, user management or the no-op administrative operations. PostgreSQL retains its prior advertisement, including stubs; neither backend's advertisement is a complete compatibility guarantee. System stream emulation and comprehensive protocol validation are not implemented. Unsupported requests may appear to the official client as generic RPC errors or retries; error mapping is not fully verified. Subscription polling has not been load-tested and no change streams or push notification mechanism exists. `$all` boundary and empty-read semantics and stream subscription reconnect, cancellation, deletion, and failover behavior need broader compatibility testing.

Run the shared official-client stream contract against a disposable single-member MongoDB replica set with `npx jest --config test/jest-e2e.json --runInBand mongodb-contract.e2e-spec.ts`. All 40 shared cases passed in the integration run, with none skipped, including adapter restart; this is not comprehensive parity or a production-readiness test. Run the other MongoDB tests with `npx jest --config test/jest-e2e.json --runInBand mongodb-infrastructure.e2e-spec.ts mongodb-streams.e2e-spec.ts`; Docker is required. They exercise official-client writes, reads, recreation, tombstones, stale revisions and concurrent expected-revision writes/deletes. The infrastructure suite also checks the actual transaction commit command, transaction abort and driver recovery after temporarily pausing a single-node replica set.

MongoDB persistent-subscription Create, Update and Delete RPCs now return gRPC UNIMPLEMENTED even when the client bypasses feature negotiation. Other persistent-subscription RPC stubs, user-management stubs and no-op administrative RPCs still need equivalent protections; direct callers can receive misleading success. The official client falls back to HTTP for several unadvertised methods, so those calls do not test the corresponding gRPC endpoints. Do not rely on capability negotiation as an access-control boundary.

Run the shared scavenging contract against a disposable single-member MongoDB replica set with `npx jest --config test/jest-e2e.json --runInBand mongodb-scavenge.e2e-spec.ts`. Its fixture explicitly opts in and restores the environment afterward. Four cases cover max-count retention and revision continuity, soft-deleted history, tombstoned history, and retention of the last truncated event. These cases do not establish scavenge completion reporting, cancellation, concurrency, failover, or full KurrentDB parity; scavenging is destructive and these tests use only disposable data. Event writes and reads use the official client; the existing shared operations test helper uses a low-level gRPC client for start-scavenge.

Run the election test separately with `npx jest --config test/jest-e2e.json --runInBand mongodb-failover.e2e-spec.ts`. It requires a local Linux Docker daemon with host networking and available loopback ports; it starts three disposable `mongo:7` containers. After an official-client append is acknowledged, the test pauses the primary, waits for a different primary, and reads the event, appends another event, and rejects a stale revision using the same running adapter. It resumes the paused container and removes only its own containers. This is one controlled process-pause election, not a proof of power-loss durability, rollback, network partitions, in-flight or uncertain commit outcomes, concurrent failover conflicts, subscription recovery, or the full backend contract.
