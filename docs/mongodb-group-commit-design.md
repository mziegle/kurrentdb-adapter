# MongoDB independent-append group commit: design history and experimental implementation

**Current status:** The application has a default-off experimental group-commit path. Its configuration, current behavior, known contention hazards, and limited measurements are documented in [the group dispatcher guide](mongodb-group-dispatcher.md#experimental-application-integration). It is not production-ready, particularly for multi-instance use. The candidate and gates below are historical design objectives, not a description or certification of the implementation.

**Prototype status:** `src/mongodb/group-commit.ts` is a state-machine component used by the experimental application path. Optional `seal(max, distinctKey)` selects the first queued member for each key in queue order and leaves duplicate keys queued in their original order; this enforces uniqueness only within that sealed group, not across active groups, and relies on the caller to provide a stable, side-effect-free key. It does not validate stream eligibility. Queue request/event/byte limits apply to queued work; `maxActiveGroups` limits nonempty sealed groups (default `maxRequests`) and `maxRetainedBytes` limits caller-declared bytes across queued and retained groups (default `maxBytes`). Admission is synchronous and selection FIFO. A full active-group limit makes `seal` throw without removing queued requests. These are logical budgets, not heap measurements: payload sizes are caller-supplied, results and external references are not measured, and values are not deep-copied. Cancellation only removes queued members; listeners and timers are detached at seal. The queue exposes `activeGroups` and `retainedBytes` for observing accounting.

**Original integration objectives (not a current implementation checklist):** enforce actual payload sizing and memory ownership and validate active-group/retained-byte limits under real transaction lifecycle; enforce group event/byte and stream uniqueness limits, client notification, overload behavior and post-seal disconnect handling; integrate shutdown with actual transaction/session lifecycle and recovery; implement transaction orchestration with safe bounded retries, definitive-abort versus unknown classification, majority+journal, overflow/size limits and no publication before acknowledged commit. Satisfy all real-client, replica-set, multi-instance and failover gates below. Unit tests do not prove database atomicity or production readiness.

**Isolated Mongo runner:** `src/mongodb/group-runner.ts` connects the coordinator to a Mongo session and is used by the opt-in application write path. It executes the callback at most once, uses majority+journal, retries labelled unknown commit results only by committing the same transaction, and reports any final commit error as unknown. The legacy `maxAttempts` option is validated but no longer authorizes work replay. The driver can retry wire commands internally, so limits do not bound wire commands or elapsed time. Invalid limits settle the batch as aborted without starting a session. `aborted` here means the runner sent no commit for any attempt; it does **not** assert that server-side rollback or cleanup completed. This depends on the supplied retry-safe callback using only the provided session and never committing, starting transactions, or performing external side effects. The callback owns database operations, safe positions, transaction duration and ordering; this runner alone cannot enforce the counter protocol.

The isolated runner's `isDefinitiveGroupAbort(error, batch)` is deliberately disabled and always returns false. Driver command-monitoring events are publicly forgeable, connection identifiers do not establish a trusted origin, and the previous observation was published only after batch settlement and ownership release. Even a genuine successful abort cannot authorize replay through this API. The driver can suppress abort failures; `aborted` only means no runner commit was sent and is not proof of rollback. No per-member replay is provided; experimental application wiring exists. The runner holds accounting until cleanup completes; cleanup failure or a hang can retain it indefinitely. The mismatched-connection forged-event test is regression coverage added after disabling evidence, not a separate RED/GREEN slice.

The isolated `mongodb-group-adapter.e2e-spec.ts` invokes the real transaction-scoped append helper through the runner against a disposable single-node replica set. The private `appendGroupMember` wraps only `StreamDeletedServiceError` as a typed member error; all other errors propagate and abort the group. The helper acquires the global counter fence before reading stream state. On the unique tombstone throw, before event or stream writes, the group helper reverses that member's counter increment within the same transaction; the counter write lock remains held until commit or abort. Thus a rejected member consumes no position, while concurrent writers and tombstones serialize or conflict at the same fence. A failed reversal aborts the group; it must not be swallowed. This relies on the unique throw site and must be revisited if it changes. The result union is staged until the majority+journal commit is acknowledged; an unknown commit discards even the staged tombstone result. No per-member replay is provided; experimental application wiring exists. Tests cover real replica-set behavior, but do not establish multi-node failover, throughput, or production readiness.

The `mongodb-group-runner.e2e-spec.ts` disposable single-node replica-set test verifies shared majority+journal commit, serial positions, session end, a transient insert failure without work replay and an exhausted failpoint commit error. Additional tests wrap the actual driver commit: after MongoDB acknowledges each real commit, the wrapper injects a lost-reply error. They verify same-session and transaction-number retries, no callback replay or duplicate persisted events, and readback after an exhausted unknown outcome. Another gates a live transaction immediately before commit, times out shutdown, and verifies the unknown outcome remains immutable even when the real commit subsequently succeeds; retained accounting is released only after cleanup. These wrappers model loss at the application/driver boundary, not a real network failure or election; direct database readback does not establish official-client behavior. Strict TDD limitation: the original runner's initial test failed to compile, and retry tests were added after implementation; these new characterization tests likewise pass existing retry behavior without a prior behavioral RED. No production change was made for them.

**Handoff limitations:** `isolate(attempt, owner)` is an assertion by the holder of the `retain()` release capability, not proof of a MongoDB abort. In particular, `GroupTransactionError('aborted')` is not a replay authorization: final work failure is classified before abort cleanup, cleanup can fail or hang, and successful session cleanup alone does not establish an acknowledged abort. The coordinator currently exposes a caller-supplied classifier, so connecting that classifier directly to `isolate` would trust an arbitrary assertion. A safe handoff needs evidence bound to the owned batch and transaction lifecycle, an acknowledged abort before replay, and an irreversible barrier after any commit attempt; failed or uncertain abort and shutdown races must never start individual transactions. Replay must preserve each actual member error and hold capacity through every individual transaction and cleanup. The caller must establish whole-transaction rollback and absence of uncertainty before invoking it; the existing runner's `aborted` classification is insufficient. Once entered, staged values are discarded and each original member can be settled once, with an explicitly supplied committed result, error, abort or unknown; no database operation or retry is initiated. Each committed result must come from a separately acknowledged operation. Existing committed/unknown batch outcomes cannot enter isolation, but this prototype cannot detect an unreported commit attempt or a dishonest caller. Sealed cancellation remains ineffective. Shutdown marks only unresolved members unknown and rejects late handoffs; retained bytes and group capacity remain reserved until the owner releases after all actual work and cleanup finish. Premature release while isolation is pending is rejected; a lost owner or hung cleanup can retain capacity indefinitely. Bounds count members and caller-declared payload bytes, not error/result object sizes. No production-ready integration, automatic retry, real database isolation test, or exactly-once guarantee is provided.

**Lifecycle constraints:** The coordinator retains each owned batch until transaction execution and session cleanup finish; client outcome is published as soon as commit or pre-commit failure is determined, before final abort/end-session cleanup. Cleanup failures emit a fixed, payload-free diagnostic via `console.error`; diagnostic exceptions are suppressed and cannot replace the transaction outcome. Failed `endSession` conservatively retains accounting indefinitely; a hanging transaction, abort or session cleanup also retains it indefinitely. There is no recovery/release API and no elapsed-time bound on the runner promise. Shutdown closes admission, cancels queued members and waits for retained work up to the timeout; at timeout it marks unresolved members unknown and returns, but does not cancel, stop or prove rollback of any in-flight transaction or session. Settled outcomes are immutable even if a late commit succeeds. Accounting remains retained until cleanup succeeds, including after shutdown; unowned sealed batches are settled/released at timeout. Timeout depends on a responsive event loop. A transaction callback and its session must not be concurrently used or independently managed by callers. A late result after shutdown may cause the runner promise to reject; callers must observe that promise. These limitations preclude production use.

**Status:** The individual-transaction path remains the default. The opt-in implementation has been measured on a limited workload; see the [measurement summary](mongodb-group-dispatcher.md#limited-performance-observation). The earlier baseline, removed local queue and round-trip experiments do not establish group-commit performance.

## Decision and blockers

The original decision was not to ship a tracer without further evidence. An opt-in experiment now exists, but the following blockers remain relevant. Independent RPCs currently have separate MongoDB transaction and failure boundaries; one group transaction makes their success and uncertain-commit outcomes correlated. MongoDB has no per-request savepoint in a transaction: a write error may abort the whole group, so catching it and continuing is not a valid isolation strategy. A safe implementation needs a proven retry/abort state machine, race-free cancellation admission, limits on shared transaction size and duration, and real multi-instance and failover evidence. The current backend intentionally ignores the propagated cancellation context; it cannot simply queue an already-cancelled request or discard a request once its writes are part of a potentially committing group. Exact error compatibility under shared failure and retry is not established. This work is more than a local batching change, and a happy-path-only tracer left enabled would not safely preserve the independent-request contract. The opt-in must not be treated as production-ready.

**BatchAppend error limitation:** A backend-thrown `StreamDeletedServiceError` for the same stream is now returned on its correlation using the existing `StreamDeleted` protocol detail; other pending correlations can continue. MongoDB and PostgreSQL already handle their ordinary tombstone and wrong-version results within their backend paths. The official JavaScript client's BatchAppend error decoder dispatches on the detail type, not the status code; it has no out-of-range detail mapping. MongoDB safe-integer failures therefore cannot be reported as an isolated, recognizable `OUT_OF_RANGE` error to that client without changing its meaning. They remain fatal to the duplex call rather than being mislabeled as a wrong version, timeout, or unknown commit. Unclassified driver errors and potentially uncertain commit outcomes also remain fatal; no replay or rollback claim is made. The injected-backend official-client isolation test covers only the stream-deleted mapping, not transaction grouping, failover, or all backend failures.

## Existing behavior and constraints

* `MongoEventStoreService.append` parses each request, starts a session and runs `withTransaction`. Its first transactional operation increments `counters/global` by the number of events (or one), then it checks stream state and expected revision, inserts events, updates retention when applicable and updates the stream. Wrong expected version and empty or recognized retry return from the callback, but still commit the counter increment. All documents and positions are committed together. A single initial exact `NO_STREAM` retry is recognized under the narrow conditions documented in [mongodb.md](mongodb.md); other retry outcomes may be ambiguous.
* `batchAppend` translates each correlation group to `append`, maps its result to that correlation and separately maps stream-deleted errors. Ordinary `Append` returns a wrong-expected-version response rather than a thrown RPC error. Preserve these mappings and current safe-integer checks, including overflow rollback. Stream deletes, tombstones and unsafe opt-in scavenging also acquire the global counter transactionally. Metastream writes can change another stream's retention policy.
* The infrastructure client explicitly sets `{ w: 'majority', j: true }`; no design may override or weaken it. A single-member majority does not provide replication redundancy. Existing `$all` polling uses event positions; assigning positions outside the counter transaction or committing an earlier position after a later one risks permanently skipping events. Existing read concern itself is not a failover-safe majority-read guarantee.
* The controller passes cancellation and deadline in `WriteRequestContext` to both append forms, but MongoDB explicitly ignores it. The old baseline report predates that propagation. A cancellation or timeout already does not prove a Mongo transaction aborted. Adding queue wait increases the period in which cancellation can occur; it must not create delayed writes for requests that cancelled while waiting.
* Six-stream exploratory baselines reported 179.23/265.47 and 181.10/304.57 Mongo/Kurrent operations per second, with unequal/unverified durability equivalence, two non-independent runs and no readback in that baseline. The removed admission queue and round-trip experiment did not meet the target. Those baseline runs did not measure group commit.

## Historical candidate, subject to validation

Use a process-local bounded coordinator only when an explicit experimental flag is exactly enabled at startup; invalid settings should fail startup rather than silently enable it. Default and mixed deployments use the existing path. Group only ordinary, nonempty, already validated single-stream append requests to **distinct ordinary stream names**, excluding `$$` metastreams, ambiguous malformed requests, and oversized payloads; bypass others through the original path. The exact eligibility must not reinterpret protocol fields or weaken validation. Batch-append correlation groups may use the same path only after their individual mapping is verified. A group is not the client's existing multi-event atomic append: each member remains a separately reported request, and its event sequence stays contiguous.

Admission must bound queue count, total event bytes and events, group size, and maximum delay, with explicit overload behavior (e.g. a documented resource-exhausted error before admission). Enforce MongoDB per-document/command limits and conservative total transaction byte/time limits; reject or bypass oversized individual requests rather than permanently head-of-line blocking them. Do not run concurrent operations on one driver session. Backpressure, shutdown, timer cleanup and per-instance memory limits are required. Fairness across instances is not guaranteed. Set limits/configuration only after exercising the real harness; this document does not prescribe guessed defaults.

At sealing, atomically remove cancelled/deadline-expired queued requests, detach their queue listeners and settle them once. Ensure races between cancellation, selection and shutdown have one owner and one settlement. Once sealed, cancellation of one member must not abort other members and must not be represented as proof of rollback; any sealed request can commit even after its caller disconnects. The gRPC deadline still controls the client's wait. Do not release results to live callers until the shared commit is acknowledged; no result from a transaction callback may escape an attempt before commit.

A proposed attempt begins one session and acquires/increments the same `counters/global` inside the transaction, before state reads, by a safe upper bound for selected event positions. Evaluate each member's expected revision, tombstone and narrow idempotent retry independently against transaction state, using the same existing response semantics. Stage successful distinct-stream events and stream updates in deterministic group order, serially on the session, and buffer per-member results. No rejected member can have staged writes; positions consumed by rejected, empty, or recognized-retry members may leave gaps, as the current path already can. Validate overflow before any commit, including total reservation, per-event position and revision. A recognized retry returns the stored position. Any update/insert error must abort the entire attempt; it is not safe to swallow a MongoDB command failure and continue. Commit all staged successes with majority+journal, then publish their individual buffered outcomes. Re-evaluate *all* state and rebuild all results on every driver transaction callback retry; no mutations to shared queue state, external responses or non-repeatable effects may leak from an aborted attempt.

Because every competing writer, delete, tombstone and scavenger still uses the same transactional counter, another instance either commits before this group acquires it or conflicts/retries and commits afterward. Contiguous positions assigned within a group become visible together, with deterministic position order, not individually committed transactions. Confirm the zero-increment lock behavior under real MongoDB races instead of assuming it. Reads can observe the group atomically rather than observing a prefix; cross-stream atomic visibility and correlated failures are observable differences from separate transactions and must be explicitly accepted for the experimental mode. Fallback individual writes may overtake queued requests; do not claim FIFO, fairness or cross-instance request-arrival order. For overlapping requests, committed position order, not wall-clock admission order, is the guarantee. A response sent only after commit preserves real-time ordering for a later request begun after that response, subject to normal uncertain failures.

## Failure, cancellation and retry policy

| Situation | Required behavior / open decision |
|---|---|
| Validation failure before enqueue | Preserve existing request-specific error; do not poison peers. |
| Cancel or deadline before seal | Remove and settle that member; it must never be written by this group. Test selection races. |
| Cancel or deadline after seal | No success promise to the cancelled client; do not infer abort or cancel peers. A commit may still happen. Document reconciliation. |
| Wrong expected version or tombstone | Derive each response independently in the transaction; other eligible members may succeed. Delay publishing even a definite rejection until the group transaction's outcome is known unless separately proven safe. |
| Transient transaction failure | Driver may retry the entire callback: re-read and rebuild every member's results; no duplicate publication. Respect bounded retry/deadline policy without misclassifying an unknown commit. |
| Definitively aborted group, e.g. non-transient insert error | No staged writes committed. A future implementation may isolate offenders by re-running smaller groups or individual transactions only after definitive abort; this changes interleavings and requires tests. Otherwise fail all members explicitly. Do not guess which request committed. |
| Unknown commit result, process crash or lost response | Treat all potentially staged members as uncertain; never split/replay as if abort were certain. Driver commit retries do not provide application-level idempotency. Reconcile individually, observing the narrowly supported `NO_STREAM` retry rule. No new exactly-once guarantee. |
| Shutdown | Stop admission, resolve queued requests without writing, and drain or explicitly classify sealed groups as uncertain; close sessions only after safe resolution. Do not hang indefinitely. |

A group-wide non-transient error is an observable regression relative to individual transactions. Whether an explicitly experimental opt-in may expose it, or must isolate by retry after proven abort, needs a product/contract decision before implementation. Likewise, define client-visible overload and cancellation status, maximum added latency and whether correlated unknown outcomes are acceptable. No option should claim ordinary request-level failure independence while allowing group-wide failures.

## Original proposed correctness gates

Use the official client and isolated real MongoDB replica sets, not only mocks or direct transaction smoke tests; follow `AGENTS.md`. First prove fixture abort/rollback and command-level majority+journal. For each slice write a failing behavior test, observe RED, implement minimally, then observe GREEN and run regressions. A first slice must verify that two eligible concurrent requests actually share one transaction/commit using command monitoring **and** both are readable through the official client with correct revisions, payload and ordered `$all` positions. Instrumentation must not expose payloads or credentials. A flag-off test must show the original path remains in use. Do not expose or retain a partial implementation that fails the gates below.

The following are proposed broader correctness gates; limited exploratory measurement has already occurred and does not imply these gates passed:

1. Distinct streams, multi-event members, same-stream bypass, mixed expected `ANY`, `NO_STREAM`, `STREAM_EXISTS` and explicit revision, including zero, stale revisions, existing tombstones, exact retry and mismatched retry; ensure each response/correlation and persisted state is correct. Exercise both Append and BatchAppend if both are eligible.
2. Queue cancellation/deadline before selection, exactly at seal, after seal, after commit and shutdown; bounded admission, timeout, oversize handling, listener cleanup, no double settlement, and no delayed write for pre-seal cancellation.
3. Deterministic injected transaction callback retries and a write failure after another member's staged work; verify no partial write, no prematurely delivered success and correct retry/isolated-error behavior. Simulate lost commit replies/unknown results without assuming abort. Exercise real server failpoints where supported, not just mocks.
4. Two adapter instances mixing grouped and ungrouped appends plus delete, tombstone and retention updates; verify expected-version races, no duplicate positions, `$all` and live subscriber order, and no cursor skips. Explicitly test metadata bypass and scavenging only on disposable fixtures with its unsafe opt-in.
5. Overflow, Mongo size and transaction limits, malformed inputs, process shutdown and repeated retries. Verify all sessions, timers and clients close. Run existing Mongo contract, cursor, infrastructure, streams, scavenge and failover suites and normal build/lint/unit tests. Run a multi-node primary-election test with in-flight and uncertain commits; passing a single-node test does not prove failover durability.

## Benchmark gate and reporting

For a stronger future performance assessment, compare flag-off and flag-on under the same pinned official-client workload and separate KurrentDB reference, including the existing six independent streams, plus varying concurrency, event sizes and group sizes. Capture actual batching distribution, queue and end-to-end p50/p95/p99 latency, errors, driver/transaction retries, throughput, `$all` delivery lag and complete official-client readback. Use separate warmups, alternating randomized target order, multiple independent fresh-server runs, controlled resources and documented hardware/versions/topology. Preserve majority+journal and explicitly note any unverified durability differences from KurrentDB; do not assert equivalent guarantees. Report measured ratios with raw outputs and uncertainty, not a projected >=80% claim. Remove the candidate if correctness or performance gates fail; retain only evidence and this design.
