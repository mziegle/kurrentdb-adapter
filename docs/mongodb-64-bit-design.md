# Proposed MongoDB 64-bit position and revision design (not implemented)

The MongoDB backend still enforces JavaScript safe integers. Do not remove that guard or interpret this document as a migration procedure ready to run. The Streams protocol uses `uint64` for positions and revisions: supporting its entire representable range requires values through 18446744073709551615, not merely BSON's signed 64-bit maximum. Actual KurrentDB limits and reserved sentinel semantics must be verified separately against a reference server. Existing numeric data can be migrated only after its provenance and consistency are established; conversion cannot reconstruct values rounded by a previous writer.

## Candidate representation and implementation

- Use `bigint` in application arithmetic, comparisons, range checks and cursors; represent absent/start/end separately, not by unchecked arithmetic on unsigned values. Check every addition/subtraction and multi-event reservation before writing. In particular, decide how a soft-delete visibility boundary after the maximum revision is represented and reject an append or tombstone that would exceed the domain atomically. Cursor comparisons must not wrap at either end.
- One candidate for storage is BSON Decimal128 containing only integral values in the selected unsigned range. It can exactly represent all 20-digit uint64 values, unlike signed BSON Long. Use Decimal128 operands consistently for writes, query bounds, counter increments, and retention fields; never convert through `Number`. Prove MongoDB `$inc`, mixed-numeric comparisons, sorting, unique indexes, driver decoding, range validation, overflow behavior and transaction rollback with the actual supported server and driver versions before adopting this design. A numeric representation also avoids lexicographic ordering of ordinary decimal strings. A different representation requires an equally explicit ordering, atomic reservation, index and migration design.
- Change the protobuf loader and generated/interface typing so 64-bit values reach the backend and leave it losslessly (for example decimal strings at the protocol boundary, with explicit checked conversion to/from bigint). Verify actual runtime serialization, not TypeScript casts. The shared `PostgresProtocolService.mapRowToReadResponse` and `postgres-value.toNumber` currently convert values to numbers; MongoDB read responses, append/batch responses, wrong-version errors, deletes, tombstones, filtered and unfiltered reads, and both subscription cursors all need auditing. Shared protocol changes must not regress PostgreSQL. Keep counts separately bounded for MongoDB driver `.limit()` rather than conflating them with positions.
- Audit all state and arithmetic: `counters.value`, `streams.revision` and `visibleFrom`, `stream_events.position` and `revision`, and `retention.truncateBefore` and `maxCount`, including max-count visibility, metadata replacement, scavenging, retry recognition and stream recreation. JSON metadata currently uses `JSON.parse`, so unsafe numeric tokens are already rounded before validation; use a lossless parser or explicitly reject unsupported tokens without first rounding. Audit `$maxAge` independently. Ensure stored data and protocol error paths are checked, not just incoming requests.
- Retain transactional serialization on the global counter and majority+journal write concern. Make overflow, invalid type and invalid state fail closed inside the transaction, with no committed event, counter or stream-state changes. Define and test idempotency, unknown commit outcomes and retry interactions separately; wider integers alone do not make the backend production ready.

## Migration blockers and requirements

An offline, versioned, restartable migration is needed before permitting upgraded writers. No tool exists yet. Stop and fence **all** old and new writers, subscriptions and scavenges for the duration; take a tested consistent backup and record the schema/version. Prevent an old binary from reopening the migrated database, including after rollback. Do not rely on an advisory marker unless every version is fenced externally: current binaries do not enforce it.

Inventory and validate every document and numeric field using raw BSON-aware reads, including missing/null fields and original BSON types. Reject fractional, non-finite, negative where invalid, out-of-domain, malformed or unexpected values. Safe integer doubles can be converted exactly as their stored mathematical values, and signed integral BSON values can be read exactly without promotion to JS number. However, an integral-looking double outside the safe range, or a value whose upstream history is unknown, can already be rounded; even an apparently safe stored value is not proof of an uncorrupted source history. Require authoritative source reconciliation or a known-good restore where provenance is uncertain; do not silently bless or reconstruct values. Verify metadata event payloads as well as materialized retention fields.

Before cutover check unique keys and global ordering, counter high-water mark against retained events, stream revision/visibility and deletion state against retained history, and retention policies against authoritative metadata. Scavenging and acknowledged retries can legitimately leave gaps or remove prior events, so contiguous sequences and equality of counter to max surviving position are not valid universal assumptions. Investigate unexplained inconsistencies rather than adjusting values automatically. Design a bounded, checkpointed, idempotent conversion to exact Decimal128, including interruption/restart, majority durability, index collision handling, concurrent access fencing, validation of every converted document and schema marker, and explicit failure/rollback procedures. Test backups and restore on production-like datasets. An old binary cannot safely operate once values exceed its safe-integer limit; a downgrade requires restoring a compatible snapshot or a separately verified reverse conversion if all data fits, not simply switching binaries.

## Acceptance tests before implementation can be called complete

Use strict red-green-refactor tests, with disposable real replica sets and the official client for end-to-end behavior. Seed boundary fixtures through a controlled, documented database fixture because generating 2^53 events is impractical. Test exact adjacent values and ordered forward/backward reads and subscriptions around 2^53, 2^63 and uint64 maximum, zero/start/end and absent sentinels, expected revision and stale errors, batch and single append, delete/recreate, tombstone, retention/scavenge and filtering. Check increments and multi-event reservations at maximum fail without partial commits; check exact return values and ordering after adapter and database restarts. Exercise concurrent writers, transaction aborts, retry and election/uncertain outcome paths. Test mixed numeric legacy BSON data, indexes, malformed and rounded values, interruption and resumption at every migration stage, fencing, backup/restore and downgrade rejection. Run the shared PostgreSQL and MongoDB contracts and lint; prove no behavior relies on a JS number beyond its exact range.

## Evidence from the current implementation

`MongoEventStoreService` uses `Number`/`Number.isSafeInteger`, number arithmetic and the shared number-based protocol mapper throughout; the retention parser uses native JSON parsing. The protocol fields are `uint64`, while the generated types and PostgreSQL helper currently use numbers. On a disposable replica set, the existing `mongodb-streams.e2e-spec.ts` tests for unsafe prepare position, unsafe stream read revision, and tombstone counter overflow passed: the first two reject rather than return rounded results, and the third verifies that the counter increment rolls back. These tests do not demonstrate full 64-bit support, migration safety, maximum-range ordering, or restart behavior.
