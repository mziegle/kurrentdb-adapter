# Probe proxy shutdown

On SIGTERM or SIGINT the application stops accepting new proxy connections, then allows existing connections up to a fixed **10 seconds** to finish before destroying the proxy's remaining client and upstream sockets. Existing HTTP/2 connections can continue to carry streams during that grace period; this TCP proxy does not send HTTP/2 GOAWAY. Idle subscriptions can therefore remain open until the deadline. Once the proxy has stopped, the application begins its normal Nest shutdown. The proxy deadline does not impose a deadline on application or database cleanup; an in-flight MongoDB transaction is not assumed aborted or forcibly declared safe to replay.

A second SIGTERM or SIGINT during shutdown immediately terminates the process with exit code 1, even if application cleanup is still running. This is an emergency escalation, not a graceful shutdown or proof of rollback. A post-listen proxy server error also initiates the same idempotent shutdown and sets a failing exit code. MongoDB shutdown waits at most one second for its tracked work, cleanup and client close; if that deadline expires, it reports that closure is unconfirmed, sets exit code 1, and returns while continuing to wait in the background. The nonzero status is sticky even if cleanup later succeeds: it reports that completion was not confirmed by the deadline, not that a write rolled back or cleanup ultimately failed. If shutdown completes within the deadline, it does not change a previously successful exit status; a definite shutdown error is also nonzero. It closes the client once tracked cleanup is confirmed, but leaves it open indefinitely if cleanup cannot be confirmed. This does not guarantee process termination; use a second signal or an external supervisor when necessary.

Forced disconnection can interrupt subscriptions and lose events not yet delivered to the client; consumers should reconnect from their last safely processed checkpoint. An interrupted or unacknowledged write has an **unknown outcome**: it may already have committed, and the disconnect does not prove rollback. Reconcile before retrying according to the application's idempotency rules.
