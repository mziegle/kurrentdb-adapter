# BatchAppend session buffering limits

Each BatchAppend session admits at most 64 incomplete plus dispatched groups, 10,000 retained events, and 16 MiB of estimated retained request data. Every fragment is estimated before admission. The estimate charges 32 bytes per visited value and 32 bytes plus three bytes per character per property name, plus three bytes per string character. Byte-array views additionally charge the full backing allocation, once per session while any retained group references it; each view itself still incurs its own value/property overhead. Shared backings are reference-counted by group, including across fragments. Incomplete groups release on end, error, cancellation or close; dispatched groups remain charged until both their response handler and registered backend work and cleanup settle. A deadline, cancellation, unknown group outcome, or stream close does not release live backend ownership. Unconfirmed or hung cleanup retains the charge conservatively even after the stream closes; it can exhaust process capacity until restart. A single oversized backing or accumulated incomplete groups can exhaust the budget. Traversal rejects repeated non-byte objects, cycles, and nesting beyond 64 levels.

Incomplete groups have an absolute 30-second lifetime from the first fragment; expiry closes the stream and releases all incomplete groups. This prevents indefinitely idle fragments from occupying the budget, but does not guarantee fairness: clients can repeatedly reacquire capacity, and hung or unconfirmed backend cleanup permanently occupies capacity until process restart. Active work is never released merely because a stream closes or a deadline elapses.

A module-level 64 MiB budget additionally covers estimated request data retained across all BatchAppend sessions in this Node.js process. It charges each backing allocation once across groups and sessions, and charges per-value and property overhead for every fragment; references remain counted through active backend cleanup. Per-session limits still apply independently. This is an estimate, not a measured V8 heap limit: decoded messages and transport buffers exist before admission, and backend allocations, response buffering, connection/session objects and other RPCs are not bounded here. Multiple Node processes each have their own budget. Limit inbound connections, transport buffers and message rate separately at the proxy/server; 4 MiB per gRPC message does not bound aggregate connection memory.

When any fragment exceeds a session or process budget, the session can return one correlated `google.rpc.Status` UNKNOWN with `event_store.client.Unknown` details and message `Append was not dispatched.` The group has not reached the backend. Its incomplete fragments are released without releasing other groups or active work. This requires a usable correlation ID and stream identifier (from an earlier fragment if needed). To bound queued rejection responses, at most 64 may await completion, the correlation key is limited to 256 characters, and the copied stream name to 4096 bytes; otherwise the stream fails closed. Input end waits for queued rejection responses.

Queued capacity rejections, including their copied stream-name backing, correlation and status metadata, are estimated against the same process budget. Tombstone keys remain charged until stream close. A group being rejected releases its incomplete request reservation before attempting the response reservation; if even the response cannot fit, the stream fails closed instead of retaining an uncharged response. On close, responses not yet submitted to the transport are discarded and uncharged; an already submitted response stays charged until its write callback, even after close. A callback that never arrives can therefore retain capacity until restart. This is conservative, not a guarantee that grpc-js promptly releases all transport allocations; ordinary success/error responses and transport buffers remain outside this response accounting.

Every rejected correlation is tombstoned for the lifetime of the stream, even after a final fragment or timeout: all subsequent fragments with that ID are silently discarded without retaining their payload. Never reuse a rejected correlation ID on that stream; the protocol cannot distinguish reuse from late fragments. A malicious client can deliberately sacrifice its own correlation by provoking rejection. At most 64 tombstones are retained; the next distinct rejection closes the stream with RESOURCE_EXHAUSTED rather than risking redispatch. Reusing an ID while a prior group remains active also fails the stream closed. Expiry of an unrelated incomplete group still closes the stream. Stream-level errors say nothing about rollback: other in-flight writes may have committed or may still commit. The installed official client has a process-wide promise bank and a stream error can reject unrelated clients' pending promises. A correlated UNKNOWN is not a rollback assertion in general; this specific message is generated only before dispatch. The installed Node client turns this response into `UnknownError` with no numeric `code`, so callers cannot rely on receiving the server message or distinguish non-dispatch from other unknown outcomes by error type alone.

The AppModule process-budget test holds 21 separate official-client sessions after their roughly 3 MiB writes commit. Another request sends an options-only fragment, then a large non-final fragment and a final fragment; a sizing spy verifies process-budget rejection of the non-final fragment and discard of the final fragment. That request receives correlated `UnknownError`, another equal-sized request remains rejected while the holds persist, and the 21 held requests succeed once released; all are readable and capacity recovers. It uses the official client, server-side observation, and a disposable single-node MongoDB replica set. This verifies non-final fragmented process-budget rejection across clients, not concurrent correlations on the same wire stream, a crash during commit, active-transaction rollback, throughput, or multi-process coordination. The count depends on allocation and message size. A separate official-client fragmented test verifies an overflowing final fragment yields `UnknownError` and a peer remains usable.
